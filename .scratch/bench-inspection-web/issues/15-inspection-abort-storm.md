# 15: 巡检：中断风暴与恢复验证

**What to build:** 多阶段流式中断（在第 1 / 16 / 64 个 token 处客户端断开）叠加并发干扰与金丝雀请求，中断后验证服务恢复。

**Blocked by:** 14

**Status:** done

- [x] 在预设的 token 处断开，且断开点按**已解析的生成事件数**计，不按 TCP chunk 或字节数计
- [x] 并发干扰下正常流与金丝雀请求不受影响
- [x] **被取消的请求不算服务失败**
- [x] 恢复验证：中断之后，健康探针与正常生成请求都必须在限期内恢复通过
- [x] 恢复失败时该用例置为 FAIL，且**后续具有破坏性的用例被跳过**
- [x] 该用例不产出吞吐、延迟或容量结论——它只回答"服务是否隔离良好、是否可恢复"

## 验证记录

24 条中断流（阈值 1 / 16 / 64 各 8 条）+ 8 条存活流 + 4 个金丝雀请求同时打过去，然后三轮恢复验证。对真实目标 PASS。

### 第一次跑是 FAIL，而且失败得很有价值

```
✗ disruption.abort_storm   FAIL   8/24 aborts went wrong
```

恰好 8 条——正是一整个阈值组。单独探测后原因清楚了：

```
threshold= 64  generated=16  done=True  finish=stop
```

**流在 16 个 token 处自己结束了**，所以客户端根本没来得及在第 64 个 token 处断开。模型觉得"Repeat the word token."答完了。

修法与业务数据集同源：加 `ignore_eos`，让长度由请求决定而不是由模型的兴致决定。

这件事值得记下来，因为我给这条用例写的注释**提前描述了它**：「流在到达阈值前自己结束，说明中断根本没发生——那是测试坏了，不是服务坏了」。设计与实现都对，只是发送的负载没有配合。

### 断开点按事件数计

`stop_after_tokens` 数的是**已解析的生成事件**（`content` 或 `reasoning_content` 非空），不是字节、不是 chunk。"客户端在第 16 个 token 处离开"是一句关于生成的话；chunk 边界是传输层的人造物，说不出这句话。

### 取消不算失败

客户端主动断开是**测试在起作用**，不是故障。所以一条成功的中断既不计入失败，也不计入错误。

### 恢复用连续多轮，不用单次

中断后答对一次可能只是恰好还有东西在飞。要求**连续三轮**（健康探针 + 真实生成并发通过）才算恢复；任一轮失败则计数归零。

### 恢复失败会连带影响后续

恢复失败 → 该用例 FAIL，且**后续破坏性用例被 SKIPPED / run_unsafe**。当前用例集里它是最后一个（它之后的状态已经被它自己搅动了），但这条规则为将来加用例留着。
