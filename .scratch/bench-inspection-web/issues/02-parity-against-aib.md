## 验证记录

对拍工具：`backend/tools/parity.py`（常驻工具，不是一次性脚本）。每边跑 **3 次独立进程**——因为 warmup 与 flush 是每进程一次，跑一次对比一次会把工具差异和机器漂移混在一起。

### 工况 B：并发 1 / 32 请求 / 输入 512 / 输出 64

低并发下没有批处理排队，单独考验逐请求计时路径。同样全部通过。

### 结论

**p50 类指标是强证据**：三个指标的 p50 差距在 **0.1%–0.9%**，而每个工具自身的 run 间波动是 0.2%–2.1%——**工具之间的差距比同一工具重复跑的波动还小**。对口径差异来说，这已经是最强的证据形式。

**p99 类指标是弱证据，且这次暴露了出来**：32 个样本时，单工具自己跑三次 p99 的波动高达 **40–48%**（numpy 线性插值下 `0.99 × 31 = 30.69`，p99 基本就是**最大值**）；64 个样本时降到 15–20%。第一次跑工况 B 时出现过 `ttft_p99` 差 33% 的 FAIL，加上噪声报告后判定为噪声——**两次运行的"最大值"之间比较，本身就不是可用的统计量**。

**两侧的波动幅度相当**（如工况 B 的 ttft_p99：ours 48.3% vs aib 39.9%），说明不是某一方实现更不稳。

### 顺带修正了工具自身的一个缺陷

初版对拍工具**只报告 p50 的 run 间波动、不报 p99**，导致 33% 的差距无法判读。现已改为：

- 每个被比较的指标都报告两侧各自的 run 间波动
- 判据从固定容差改为 **`allow = max(固定容差, 噪声)`**，并把"容差来自噪声"用 `*` 显式标出

这样一次"通过"永远不会掩盖"这个统计量本身就不稳"。

### 本工单**没有**验证的一件事

**对拍没有考验 cache flush 的有效性。** 合成 prompt 是每个请求现抽的随机 token，请求之间不共享前缀，缓存命中率本来就接近 0——所以 flush 生效与否在数字上看不出来。当前 flush 的唯一保障是：客户端在 flush 未返回 200 时会**主动中止**，拒绝在热缓存上测量。

要让 flush 变得**可观测**，需要构造共享前缀的 workload（即 `cache_ratio > 0`）。这是一个尚未存在的 workload 形状，建议单独开工单。
